## 24/09/2026 — P1 (multi-tenancy stancl v3.10)

| # | Décision | Détail | Réf. |
|---|---|---|---|
| D-018 | **Nommage des bases cabinets** | `prefix='cabinet_'` + slug ⇒ `cabinet_<slug>`. Bootstrappers actifs : Database, Filesystem, Queue ; cache isolé par tenant **uniquement** si Redis (`file` → non inclu). | T1.2/T1.4 |
| D-019 | **Queue centrale + sessions/cache file + timezone** | `DB_QUEUE_CONNECTION=pgsql` (jobs en base Landlord, indépendante du tenant courant) ; `SESSION_DRIVER=file`, `CACHE_STORE=file` ; `APP_TIMEZONE=Africa/Ouagadougou`. | T1.4 |
| D-020 | **Découpage routes** | `routes/landlord.php` (domaine central, web) ; `routes/tenant.php` = 10 fichiers web KEduc sous `InitializeTenancyByDomain` + `PreventAccessFromCentralDomains` ; groupe `api` tenant-scope (landlord API à préfixer séparément en P3). | T1.5 |
| D-021 | **Migrations : 4 landlord / 75 tenant** | Landlord = stancl (`tenants`/`domains` + colonnes cabinet) + infra (`cache`, `jobs`) ; tenant = schéma KEduc dans `database/migrations/tenant/`, `cabinet_id` retiré de `faq_sections`, `uuid_client` (unique) ajouté à `cahier_textes`. | T1.3 |
| D-022 | **Données cabinet du tenant (D-014)** | Table tenant `parametres_publics` (1 ligne : `theme` json, `footer` json, `data`) + `CabinetInfo` (source tenant, repli temporaire `keduc.cabinet`). Les 4 services PDF vivants, `FactureWebController` et 7 vues ne lisent plus la config statique. | T1.6/T1.7 |
| D-023 | **Tests d'isolation : base `keduc_test` non transactée** | `phpunit.xml` pgsql : `DB_DATABASE=keduc_test`, `TENANCY_DB_PREFIX=keduc_test_` (D-003), envs en `force="true"` (surcharger le `.env` chargé par `artisan test`). PostgreSQL interdit `CREATE DATABASE` dans une transaction → `connectionsToTransact()=[]` + `migrate:fresh` avant **chaque** test (`RefreshDatabaseState::$migrated=false`) ; bases tenant supprimées en tearDown. | T1.9 |
| D-024 | **`Cabinet::getIncrementing()=false`** | Avec `id_generator => null`, stancl ne lie pas le générateur ⇒ Eloquent traite l'id comme auto-incrément et insère sans `id` (colonne varchar → `0`). L'id (= slug, D-005) est donc toujours fourni manuellement, jamais auto-incrémenté. | T1.9 |
| D-025 | **Pipeline stancl non transacté** | Le pipeline `TenantCreated` (CreateDatabase → Migrate) exécute `CREATE DATABASE`, interdit dans une transaction PostgreSQL ⇒ aucune étape du pipeline n'est encapsulée dans `DB::transaction`. | T1.9 |
| D-026 | **Echec pipeline = rollback manuel** | En cas de bug dans `CreerAdminCabinetEtNotifier`, le catch du pipeline annule l'ensemble : suppression de la base (TenantDeleted/DeleteDatabase), puis `DELETE` SQL direct sur `tenants`/`domains` (éviter de re-déclencher TenantDeleted) ; journal `cabinet.echec`. | T2.4 |
| D-027 | **`Cabinet` = colonnes contrôle à plat (VirtualColumn)** | stancl sérialise dans la colonne json `data` tout attribut hors `getCustomColumns()`. `email`/`telephone` du cabinet sont donc déclarés colonnes (id, sous_domaine, statut, créé à la création, etc.) et restent des attributs top-level fillable — jamais sous une clé `data`. | T2.3 |
| D-025 | **Tenant inconnu → 404** | `TenantCouldNotBeIdentifiedException` rendue en `404` (JSON `{message, code: CABINET_INCONNU}` si `expectsJson`, sinon 404). Le `/` appartient aux cabinets : `routes/landlord.php` est vide (trappé par `PreventAccessFromCentralDomains` sur les domaines centraux) pour éviter la collision avec le `/` tenant. UI Landlord en P2. | T1.5/T1.9 |
| D-026 | **Suite Legacy KEduc mise de côté** | 19 fichiers / 195 tests monolithe web déplacés dans `tests/Feature/Legacy/` (exclus de la suite par défaut) — obsolètes sous tenancy (rôles/permissions en base tenant, domaines). Réécriture par module API dès P3. | T1.9 |
| D-027 | **Seed automatique à la création + page publique blindée** | `Jobs\SeedDatabase` ajouté au pipeline `TenantCreated` (CreateDatabase → MigrateDatabase → SeedDatabase, sync en dev) : tout nouveau cabinet est provisionné complet (rôles/permissions/référentiels/`parametres_publics`, T1.7). `HomeController` : la requête `role('enseignant')` n'est exécutée que si le rôle existe (collect sinon) — un cabinet non seedé n'explose plus en 500. | T1.7/T2.4 |
| D-028 | **Assets publiques hors brouillage tenant** | `FilesystemTenancyBootstrapper` réécrivait `asset()` vers `/tenancy/assets/<...>` (stockage tenant route par Laravel) : les CSS/JS de `public/` 404 → site « sans CSS ». Fix : `tenancy.filesystem.asset_helper_tenancy = false` — `asset()` reste sur la racine publique ; le suffixage de `storage_path()` et des disques (isolation uploads) est conservé. Les assets tenant explicites utiliseront `tenant_asset()` (P3). | T1.4 |
| D-029 | **Console Landlord : `super_admins` + guard `landlord`** | Table centrale `super_admins` (D-015) ; modèle `SuperAdmin` avec `CentralConnection` ; guard/provider `landlord` (session → `super_admins`). Routes `/admin` (préfixe partagé avec le backoffice KEduc mais aucune collision d'URI exacte) — murées par 3 middlewares : `landlord.auth` (authentifié requis), `landlord.guest` (déjà connecté → dashboard), `central.domain` (hors domaines centraux → 404). Le Landlord n'est jamais exposé sur un domaine cabinet. | T2.1 |
| D-032 | **Pipeline de création : admin + notif + journal, rollback total** | `CreerAdminCabinetEtNotifier` en 4ᵉ étape du pipeline `TenantCreated` (après SeedDatabase) : crée l'admin cabinet (rôle `admin_cabinet`, email du cabinet sinon `admin@<slug>.local`, mot de passe `CABINET_ADMIN_PASSWORD` ou aléatoire), envoie `CabinetIdentifiants`, journalise `admin_cabinet.cree`. Échec → rollback (DB + tenants + domains + parametres en SQL direct, pour ne pas redéclencher TenantDeleted) + `cabinet.echec`. Table `journal_plateforme` **sans FK tenant** (l'audit doit survivre au rollback/suppression). Email/telephone du cabinet sont des attributs top-level du modèle `Cabinet` (VirtualColumn les sérialise dans `data` — un attribut nommé `data` serait écrasé) → ajoutés à `$fillable`. Hook de test : `TENANCY_SIMULATE_ECHEC`. | T2.4 |
| D-031 | **`parametres_cabinet` + CRUD cabinets (Landlord)** | Table centrale `parametres_cabinet` (1 ligne/cabinet : tarif_abonnement, tarif_par_eleve, fonctionnalites_activees json ; FK vestiges-on-delete). Module `Landlord\CabinetController` : index (recherche id/nom), création (slug regex `^[a-z0-9]+(-[a-z0-9]+)*$` → `tenants.id`, auto-provision pipeline D-027, domaine `<sous_domaine>.localhost`, hors `DB::transaction` — `CREATE DATABASE` interdit en transaction), fiche, modification (nom/sous-domaine/statut/contact), tarifs+fonctionnalités (liste `MODULES`). Le seeder de test `tests/TenantTestCase.php` centralise migrate:fresh non transacté + drop des bases tenant (D-023). | T2.3 |
| D-030 | **Layout Landlord** | `landlord/layouts/app.blade.php` : sidebar (Tableau de bord / Cabinets / Facturation / Journal, lien `active` par `routeIs`, asset publics), topbar avec déconnexion, CSS `landlord.css`. Sections non encore implémentées servies par `SectionPlaceholderController` (placeholders T2.3/T2.7/P7). Aucune librairie de composants ajoutée — Blade classique. | T2.2 |
| D-033 | **Cycle de vie cabinet (T2.5)** | Statuts `actif`/`suspendu`/`archive`. Le middleware `cabinet.actif` (déjà dans le groupe web tenant) bloque en 403 tout accès dès `status ≠ actif` (JSON `CABINET_SUSPENDU` si `expectsJson`). Actions Landlord sur la fiche (`POST /admin/cabinets/{id}/statut`) : suspendre / réactiver / archiver, chaque passage journalisé (`cabinet.suspendu`, `cabinet.reactive`, `cabinet.archive`). **Suppression définitive** (`DELETE /admin/cabinets/{id}`) : sauvegarde `pg_dump` préalable obligatoire vers `storage/app/backups/<id>-<timestamp>.dump` (hook test `TENANCY_SKIP_BACKUP`), journal `cabinet.supprime`, puis destruction (parametres → domains → `tenants` → `TenantDeleted`/`DeleteDatabase` drop la base). Aucune suppression sans sauvegarde. | T2.5 |
| D-034 | **Impersonation Landlord → admin cabinet (T2.6)** | Feature stancl `UserImpersonation` activée. Flux jeton **à usage unique (5 min)** : le Landlord clique « Impersonner » (`POST /admin/cabinets/{id}/impersoner` — refusé si cabinet non actif ou sans `admin_utilisateur_id`) → `tenancy()->impersonate()` crée un jeton en table centrale (`tenant_user_impersonation_tokens`, colonne `super_admin_id`), redirige vers `GET <domaine>/impersonation/{jeton}` qui : vérifie tenant cible / expiration / utilisateur, `Auth::guard('web')->login(user)`, pose une session `impersonation`, journalise `impersonation.debut`, supprime le jeton. **Cible** : admin créé par le pipeline (`tenants.admin_utilisateur_id`, colonne réelle via VirtualColumn). **Bannière** violette en haut du layout `panel` (idempotente, conditionnelle à la session) avec bouton `POST /impersonation/sortir` (journalise `impersonation.fin`, logout). L'accès à la table des jetons passe toujours par la connexion centrale `pgsql` (page tenant sinon retournée). Statistiques : la Feature ne fournit ni cookie ni bannière ni sortie — tout est projet. | T2.6 |
| D-035 | **Écran Journal (T2.7)** | `JournalController` : consultation `journal_plateforme` (filtres action/niveau/cabinet, pagination 20, tri desc), vue `landlord/journal/index.blade.php` avec badges de niveau et contexte JSON pliable (`<details>`). Placeholder `journal` de T2.2 remplacé. | T2.7 |
| D-036 | **Commande `cabinet:migrer-tous` (T2.8)** | Enveloppe de `tenants:migrate` : itère les cabinets (`--tenant=` pour un seul), sauvegarde pg_dump préalable via `App\Support\SauvegardeCabinet` (service partagé avec la suppression T2.5, option `--force-nosauvegarde`, hook `TENANCY_SKIP_BACKUP`), migration via `Artisan::call('tenants:migrate', ['--tenants' => [$id]])`, rapport tabulaire et journal `cabinet.migre` (ok) / `cabinet.migre.erreur`. | T2.8 |
| D-037 | **Interrupteur web KEduc (T2.10)** | Table centrale `parametres_plateforme` (clé/valeur json) + `ParametresPlateforme::obtenir/definir`. Middleware `keduc.web` (404) appliqué au groupe web tenant ; **routes d'impersonation hors groupe** pour rester toujours disponibles (sinon Landlord prisonnier). Écran Landlord `admin/parametres` (interrupteur + lien sidebar). L'API n'est jamais concernée. Tests : `LandlordParametresTest` (4). Attention test : `actingAs('landlord')` force le guard par défaut → restaurer `auth.defaults.guard=web` avant de visiter un domaine tenant. | T2.10 |

## Conventions permanentes

1. Toute ambiguïté → `docs/QUESTIONS.md` avec option par défaut, appliquée, continuée.
2. Ne jamais exécuter de commande modifiant la base de données (AGENTS.md) — les formuler pour le propriétaire.
3. Ne jamais supprimer le code KEduc existant sans demande explicite → le geler et le documenter.
4. Une tâche = tests verts + case cochée dans `PLAN.md` + éventuelle ligne ici + commit.
